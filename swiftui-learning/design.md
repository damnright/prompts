## 1. 先回答谁拥有数据

以下是一种适合当前练习的方案，不要求为所有页面套同一种架构：

| 数据 | 所有者 | 子页面如何使用 | 何时结束 |
| --- | --- | --- | --- |
| 模拟词条集合 | 列表功能的模型，由稳定父级持有 | 读取词条，发送按 ID 更新的动作 | 当前练习功能结束；当前不持久化 |
| 当前筛选与选中 ID | 负责该导航 / 列表的页面 | 传入筛选结果与选择 | 按返回和重入规则保留或重置 |
| 编辑草稿 | 编辑页 | 输入绑定到草稿 | 保存成功或取消 |
| 加载状态与当前请求标识 | 负责加载的模型 | View 展示状态并发出重试动作 | 加载结束、取消或新请求取代 |
| 未来服务端词条 | PostgreSQL / Go 服务 | 客户端持有可刷新副本 | 遵循服务端的数据生命周期 |

`State` 持有局部状态或模型实例；`Binding` 传递对既有状态的读写入口；`@Bindable` 从 observable 模型获得所需绑定；Environment 用于在层级中提供明确依赖。选择它们以前先写清所有权，不能用“都放全局环境”代替设计。

## 2. 页面生命周期不是业务生命周期

页面可能多次出现、重新计算或改变身份。“页面出现”不能直接代表“用户完成一次学习”。需要持久记录的业务动作，应由用户动作、服务端确认和去重规则决定。

页面绑定任务适合加载当前所需数据；必须跨页面持续完成的工作需要另一个明确的所有者。当前先实现可取消的加载，不提前建立全局任务系统。

## 3. 评审一份问题方案

| 方案 | 触发问题的例子 | 修改方向 |
| --- | --- | --- |
| body 里创建模型并立即加载 | 状态变化触发重新求值，模型与请求不断重建 | 由稳定层持有模型，把加载接入明确的生命周期 |
| 每行生成一个临时 UUID | 列表刷新后身份变化，编辑 / 选择错乱 | 使用数据自身的稳定 ID |
| 编辑直接写共享对象，但取消只关闭页面 | 用户取消后列表已被修改 | 明确即时保存语义，或使用独立草稿与提交 |
| 捕获所有错误后设置失败状态 | 取消离开的页面也弹错误 | 区分取消与失败，并核对当前请求身份 |
| A、B 搜索按返回顺序覆盖列表 | A 先发后到，覆盖更新的 B | 取消无用工作，并拒收过期结果 |
| 固定行高和文字大小 | 大字体裁切，辅助操作无法完成 | 使用语义文字样式与可伸缩布局，在目标场景实测 |
| View 中写入数据库密码并直连 | 客户端成为数据访问边界，凭据泄露 | 只访问 Go API，凭据与业务权限留在服务端 |

## 4. 进入真实 API 前确认

把“谁产生数据、谁保存、谁刷新、谁处理失败”画成一条路径。网络 DTO 不必等同于界面全部状态；加载状态、编辑草稿和导航不应该被塞进后端词条对象。

接入网络后，先采用保存成功再更新界面的简单策略；乐观更新与离线冲突需要额外的回滚和对账，不作为第 5～6 项前置。跨账号缓存与同步在后续客户端、安全条目中处理。
