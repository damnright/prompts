# PostgreSQL 数据库设计与评审补充

[章节导读](README.md) · [实操步骤](practice.md)

这里补充业务建模和架构判断。基本概念、命令和例子按章节导读学习；第 2～3 单元先看八表案例，理解并发、索引、迁移与系统边界后再做评审。

## 1. 从需求到模型：先确定数据的含义

设计前先写“每行代表什么”和“哪些情况绝不允许发生”。主键解决记录身份；业务唯一性、用户归属、历史保留仍需分别设计。

| 数据类别 | 本例 | 设计时需要决定什么 |
| --- | --- | --- |
| 业务实体与关系 | 用户、词、组、组成员 | 身份与生命周期；一对多、多对多关系；重复成员是否允许 |
| 历史事实 | 一次作答事件 | 重试如何识别，是否允许更正，需要保留哪些上下文 |
| 当前状态 | 某用户对某词的进度 | 以谁为粒度，谁负责更新，并发更新如何协调 |
| 历史快照 | 会话创建时的目标词与展示文本 | 来源之后变化，过去的会话是否仍能解释 |
| 派生结果 | 正确率、待复习列表 | 权威输入是什么，计算口径、时区与算法版本是什么 |

把词组成员分表，有利于避免同一关系的重复表达及更新、删除异常。保留会话快照则是为了表达历史：快照与当前词条承担不同职责。是否冗余要结合业务语义判断；可重算的状态也必须具备足够输入与明确算法。

约束、事务、并发协议和应用授权各解决一部分正确性问题。主键使用 UUID 不等于业务不会重复；外键验证存在或归属，不会自动替 Go 检查当前请求者的权限。需要确认数据库的保证范围时，查阅章节导读中第 2、3、6、8 单元及官方查证表。

## 2. 英语 App 八表案例

### 2.1 业务假设与表粒度

业务假设：

- 用户拥有私人单词组，词条来自共享词库；词条区分语言、词形和词义。
- 会话可来自私人组或临时选词，保留当时目标词与展示文本。
- 作答保留为事件，同一次事件重试不产生第二条记录。
- 每用户每词一份当前进度；若要求重建，需保留足够的事件输入与算法版本。
- 本例不包含订阅、音频、离线合并算法或完整 Go 写入流程。

实操要点：表粒度、成员关系与历史快照、组合唯一性、归属外键、范围与非空约束、关键读取索引。

| 表 | 每行含义 | 在 SQL 中重点核对 |
| --- | --- | --- |
| app_users | 一个账号 | 稳定主键 |
| app_words | 一个语言、词形与词义条目 | 组合业务唯一性 |
| app_groups | 一个用户的私人组 | 所有者、可引用的 id + user_id |
| app_group_words | 一个组的成员词 | 组合主键、组内位置唯一 |
| app_sessions | 一次学习会话 | 用户请求键、来源归属、状态与时间 |
| app_session_words | 本会话的一个目标词 | 组合主键、展示文本快照 |
| app_review_events | 一次作答事件 | 用户事件键、会话所有者、目标词、评分范围 |
| app_word_progress | 一位用户对一个词的当前进度 | 用户 + 词唯一、版本、算法版本与复习时间 |

### 2.2 对照模型与提出设计

可运行文件为 [model.sql](model.sql)，运行方式及预期结果统一见[实操第 3.4 节](practice.md#model)。

1. 先根据业务假设自己列出实体与关系，再对照模型。
2. 在每条失败检查旁找到对应约束；说明它防止了什么。
3. 说明只存 group_id、只保留最后作答、只用 UUID 主键分别会遗漏什么。
4. 写出“保存作答 + 更新进度”的事务步骤、同键载荷检查与并发协议；模型脚本没有替你实现这些应用流程。
5. 为待复习列表、最近会话、作答明细各写出查询范围和排序，匹配模型中的三个索引。
6. 说明删除或归档组之后，历史查询应如何表现。
7. 进入本页[设计与评审练习](#exercises)，完成收藏功能设计与问题方案评审。

此实操验证结构和列出的约束；真实授权、并发进度更新、迁移、恢复与生产性能仍需各自的实现与验证。

## 3. 设计评审清单

你应该能从业务需求写出实体、关系、核心不变量和读写流程；遇到一份设计，能给出具体反例、影响和更合适的取舍。知道关键字名字不算充分，要求每个方案都使用复杂技术也不是架构能力。

下面按完整设计的不同层次进行评审，不要求背语法。

### 3.1 业务与模型

- 每张表的一行能否用一句话解释？有没有把事件、当前状态和统计混在一起？
- 实体关系与可选性是否清楚？多对多是否需要成员表？
- 主键是否稳定？业务唯一性的范围是否正确？
- 哪些是权威数据，哪些是快照、缓存或可重算结果？
- 修改与删除后，历史含义是否改变？是否符合已声明的数据生命周期？
- 哪些关键需求还没有确认，当前方案基于什么假设？

### 3.2 正确性与并发

- 非空、范围、唯一和引用关系分别由什么保证？
- 外键只验证存在，还是也验证必要的归属关系？
- 什么修改必须一起提交？事务中是否包含慢的外部调用？
- 两个请求同时执行时，会不会重复写入、超额、覆盖状态或接受过期动作？
- 幂等键的作用范围、载荷一致性和返回原结果协议是否明确？
- 发生死锁、序列化失败或提交结果未知时，怎样重试与核对？

### 3.3 查询、索引与容量

- 三到五个关键读写场景是否明确了用户范围、返回粒度和数量上限？
- JOIN 是否改变粒度导致重复统计？零记录如何表示？
- 索引是否能解释为某个访问需求，而不是每列随便加一个？
- 分页是否有稳定排序？读副本延迟是否破坏写后读体验？
- 是否有代表性数据上的计划与延迟证据？小表测试不能替代容量评估。
- 连接预算是否包括自动扩容、滚动发布和 worker？

### 3.4 演进、边界与恢复

- 运行角色是否拥有超出业务所需的权限？用户身份如何传递到查询？
- 结构变更如何兼容旧数据和旧应用？回填是否可中断、重入和核验？
- 删除或类型变更是否存在不可逆数据损失？回退方案是否实际成立？
- 备份恢复目标、恢复演练和外部对象存储关联是否完整？
- 长事务、锁等待、连接等待、清理落后和备份失败如何被发现并处理？

### 3.5 一份够用的设计说明模板

不需要写厚重方案。针对一个业务模块，填写以下内容即可形成可讨论的设计：

```text
业务范围：要支持哪些动作，暂时不支持什么？
关键假设：哪些规则尚未确定，当前按什么处理？
实体与粒度：每张表的一行代表什么？
关系与标识：主键、外键、唯一范围、归属关系是什么？
不变量：哪些状态绝不允许，由谁保证？
数据类别：事实、当前状态、快照、派生值分别在哪里？
关键读取：输入范围、结果粒度、排序、数量上限、索引候选。
关键写入：事务边界、竞争点、幂等协议、失败与重试。
生命周期：修改、更正、归档、删除和数据保留行为。
演进与运行：迁移兼容、连接预算、权限、备份与恢复。
验证：哪些反例与运行证据能证明设计满足规则？
取舍：选择理由、已知代价、什么时候需要重新评估？
```

## 4. 设计与评审练习

### 4.1 练习 A：自己设计一个小功能

需求：“用户可以收藏单词；取消收藏不删除历史作答；同一词可被不同用户收藏；重复点击收藏不能产生两条收藏记录；按最近收藏时间翻页。”

请先用自然语言写出表的粒度、唯一性、时间字段、删除行为、并发写入方式和索引候选。允许 AI 帮你生成 DDL，但你应能解释每一个字段与约束。

进一步考虑：取消后再次收藏，最近收藏时间是否重置？需不需要保存每次收藏事件？这会导致不同模型，没有一种答案对所有产品都正确。

### 4.2 练习 B：评审一份有缺陷的设计

以下是一个**故意有问题的提案，供阅读，不要执行**：

```text
users(id UUID 主键, email TEXT)
groups(id UUID 主键, user_id UUID 外键, word_ids TEXT)
sessions(id UUID 主键, user_id UUID 外键, group_id UUID 外键,
         status TEXT, started_at TEXT, total_minutes FLOAT)
progress(word_id UUID 主键, user_id UUID 外键,
         last_answer JSONB, score INTEGER CHECK(score >= 0), updated_at TEXT)

组成员用逗号分隔 ID 保存；回看历史时读取组当前内容。
每次作答只覆盖 progress.last_answer，不保存事件。
先查询 request_id 是否处理过，再写入；没有请求唯一约束。
进度先读到内存，计算完后无条件覆盖写回。
把 LLM 调用放在数据库事务中，等模型返回后才提交。
所有 SQL 接受客户端传入的 user_id。
给所有列分别加索引，列表仅按 started_at 排序。
新增必填字段时直接改表并立刻发布；回滚就删掉新字段。
配置一个副本，因此不再准备备份恢复方案。
API 扩容时，每个实例仍使用原来的大连接池。
```

你的评审至少回答：问题在哪、什么情况下触发、实际影响、推荐怎么改、还需要确认什么。不要只写“缺索引”“加事务”“不规范”。

先完成自己的判断，再打开 [参考评审](#answers)。

## 5. 参考评审

先形成自己的判断，再对照以下参考；业务假设不同，合理方案也可能不同。

### 5.1 收藏功能的一种合理设计

在“只需要当前收藏，不要求收藏操作历史”的假设下：一行代表某用户当前收藏某词，组合键 `(user_id, word_id)` 保证唯一，保存本次收藏的 created_at。

插入使用数据库唯一约束处理并发重复；重复收藏保持原收藏时间。取消时按当前用户和词删除这条关系，不删除词或作答历史。取消后再收藏产生新的 created_at，因此在最近收藏列表中靠前。

索引候选是 `(user_id, created_at DESC, word_id DESC)`；分页游标使用相同字段与顺序。访问范围中的 user_id 来自认证身份。

这只是一个明确假设下的方案。如果产品要统计收藏与取消的历史，就应另存事件或审计记录；如果产品要求首次收藏时间永久保留，也要额外表达，而不是悄悄改变 created_at 的含义。

### 5.2 有缺陷提案的逐项评审

| 问题 | 可触发的反例与影响 | 推荐方向 |
| --- | --- | --- |
| progress 只以 word_id 为主键 | 两个用户学习同一词，无法分别保存进度 | 以 user_id + word_id 表达状态粒度 |
| word_ids 是逗号串 | 重复、无效 ID 或顺序修改难以约束，关联查询复杂 | 用成员表，声明成员唯一性和需要的位置规则 |
| 历史只读当前组 | 编辑或删除组后，过去会话的目标变化或丢失 | 保存会话目标与必要快照，决定来源关联的生命周期 |
| 只留最后作答 | 无法重算准确率、检查算法变化或解释状态 | 保存作答事件，当前进度作为可更新状态 |
| user_id 与 group_id 仅分别有外键 | 甲会话可引用乙组，两者都存在所以不报错 | 归属组合约束或等价的可靠机制，并做应用授权 |
| CHECK 只有下界且可空 | NULL 或超出业务上限的分数仍可通过 | 明确评分语义，使用合适范围与非空约束 |
| 时间是任意 TEXT | 不同格式、偏移和排序造成错误 | 根据时间点或日历日期选择类型，并声明统计时区 |
| 时长使用 FLOAT | 单位不清或需要精确相等时产生问题 | 明确单位，按场景选整数或 interval；不要一概否定所有浮点用途 |
| 先查 request_id 再写 | 两个并发请求都判断不存在，重复入库 | 为业务键设置唯一约束，定义重复与载荷冲突处理 |
| 无条件覆盖进度 | 两次有效更新相互覆盖，丢失学习效果 | 原子更新、版本比较、行锁或合适隔离策略 |
| LLM 调用放事务内 | 慢响应长期占连接和锁，外部失败放大资源堆积 | 外部调用与数据库短事务分阶段，明确中间状态 |
| 相信客户端 user_id | 改一下参数即可访问其他用户数据 | 服务端根据认证身份确定范围，越权测试覆盖读写与批量接口 |
| 所有列加单列索引 | 写入成本增加，关键组合筛选排序仍未解决 | 从关键访问模式提出候选，再测计划和延迟 |
| 仅按时间分页 | 同时刻记录顺序不稳定，可能重复或漏项 | 补唯一排序键，选择合适游标与一致性要求 |
| 必填字段直接上线 | 旧数据不满足、旧服务无法写入，变更可能长时间阻塞 | 兼容扩展、回填核验、切换后加强约束 |
| 删除新字段当作回滚 | 新数据不可逆丢失，旧代码也未必可兼容 | 区分应用回退、前向修复与数据恢复 |
| 有副本就不做备份 | 误删复制到副本，无法回到之前 | 定义恢复目标，配置相应备份与日志保留并演练 |
| 扩容不调整连接预算 | 实例翻倍后数据库连接总量超过承受范围 | 按最大重叠实例数计算总预算，并控制工作并发 |

### 5.3 还不能直接判错、需要先确认的地方

users.email 是否应该唯一，取决于账号模型、登录方式、大小写与规范化规则。某些产品允许无邮箱账号，某些允许多个身份关联同一主体。不能在缺少规则时机械要求所有邮箱全局唯一。

是否必须为所有外键建立索引、是否需要软删除、是否需要 RLS、是否引入副本，也都需要结合访问模式、规模和风险。评审质量体现在能说明前提和取舍，而不是技术名词越多越好。

### 5.4 改完表以后，还需要哪些验证？

- 并发重复提交同一事件：只能产生一次业务效果，重复载荷不一致应明确失败。
- 两个用户同时学习同一词：进度彼此独立。
- 同一用户两个有效更新竞争：不得无提示丢失其中一个更新。
- 修改来源组后回看会话：仍能解释当时的目标与题面。
- 身份不匹配的读写：服务端拒绝；数据库拒绝所声明的跨归属关联。
- 迁移过程中同时运行新旧代码：兼容策略实际成立。
- 恢复到隔离环境后运行关键查询：恢复的不只是一个文件，而是可用数据与必要配置。

这些是产品实施时的验证要求。本地模型演示只验证其列出的结构与约束，不应声称已经完成上述所有系统级测试。

## 6. 如何判断达到学习目标

| 能力 | 可观察的表现 |
| --- | --- |
| 基础识读 | 能解释表、约束、查询、事务与索引的职责，不把 SQL 执行成功当作设计正确 |
| 独立建模 | 能从收藏或会话功能推导粒度、关系、历史和状态，并说明备选方案的代价 |
| 正确性评审 | 能构造跨用户、重复请求、并发覆盖和错误统计的反例 |
| 访问设计 | 能为关键查询提出索引候选，并说明还需要哪些性能证据 |
| 系统意识 | 能考虑连接预算、在线迁移、数据保留、备份恢复与外部副作用 |
| 与 AI 协作 | 能审核 AI 生成的 DDL / SQL / Go 事务流程，而不是只验证语法能运行 |

遇到语法不熟可以查本地示例或让 AI 补齐。遇到业务含义不明确，应回到需求确认，而不是先让 AI 猜一个字段。
