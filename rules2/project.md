# Project Agent Rules

> 适用于 Claude Code 与 Codex。将本文件内容同步到项目根目录的 `CLAUDE.md` 和 `AGENTS.md`。全局规则同时生效；更具体目录中的规则优先，规则之间应避免冲突。

## 1. 开始任务前

先获取足够上下文，再开始修改。按需读取：

- 当前目录及上级目录中的 Agent 规则；
- `README`、`docs`、架构和开发说明；
- 依赖、构建、测试、lint、类型检查和环境配置；
- 目标代码、真实调用链、相邻实现及相关测试。

已有项目约定优先于个人偏好和通用惯例。不要仅因“更喜欢另一种方式”替换现有架构、库、命名或代码风格。

## 2. 范围控制

- 只修改完成当前任务所必需的文件和逻辑。
- 禁止无关重构、大范围格式化、擅自升级依赖或改变公共接口。
- 不为假设中的未来需求增加抽象、配置或兼容层。
- 修改生成文件、锁文件、迁移文件或公共 API 前，确认它们确实是本任务所需。
- 保留用户和其他工具已有的未提交修改；不要回滚、覆盖或清理与当前任务无关的变更。
- 发现相关但不属于当前任务的问题时，只报告，不自动扩大范围。

## 3. 计划与执行

- 简单任务直接执行。
- 复杂任务先形成简洁的内部计划，再按步骤实施和验证。
- 仅在跨会话、多 Agent 协作、重大改造、高风险变更或用户明确要求时，创建持久化计划文件。
- 普通、可逆的实现选择无需等待批准；按全局规则的确认边界处理高风险事项。

## 4. 实现要求

- 修改前确认问题根因、影响范围和依赖关系。
- 优先复用项目现有模式、公共能力和成熟实现。
- 保持改动局部、清晰、可维护；避免重复逻辑和无必要抽象。
- 除非需求明确要求，保持已有行为、数据格式和公共接口兼容。
- 正确处理错误、边界条件、空值、异常路径和资源清理。
- 不留下虚假实现、无说明的占位代码、失效注释或仅为通过检查而添加的绕过。
- 第三方、vendor 或自动生成代码应修改其源头，而不是直接修改产物；确需直接修改时说明原因。

## 5. 测试与验证

- 修改后执行与变更直接相关的验证，先窄后宽。
- 优先使用项目已有命令：单元测试、集成测试、类型检查、lint、构建和端到端测试。
- 修复缺陷时，尽可能增加能复现问题并防止回归的测试。
- UI 变更在条件允许时进行真实浏览器、关键状态和响应式验证。
- 不通过删除测试、放宽断言、关闭规则或添加忽略项来制造“通过”。
- 无法执行某项验证时，明确说明未验证内容、原因和剩余风险。

## 6. 文档与项目事实

以下长期变化应同步更新相应文档：

- 公共 API、数据结构或外部行为；
- 项目结构、开发命令或配置方式；
- 环境变量、部署流程或运行要求；
- 团队需要长期遵守的工作约定。

不要为一次性实现过程创建永久文档。项目初始化后，应在本文件末尾补充真实的技术栈、目录约定、常用命令和敏感区域。

## 7. 完成标准

任务完成至少满足：

- 用户目标已实现；
- 改动范围最小且无明显无关修改；
- 相关测试或验证已执行并报告结果；
- 必要文档已同步；
- 没有通过绕过校验掩盖问题；
- 未完成项、假设和风险已明确说明。

最终说明应包含：完成摘要、主要变更文件、验证结果，以及存在 Git 变更时的建议 commit message。
