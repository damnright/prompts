# 产品判断补充：从假设到开发取舍

[章节导读](README.md) · [实操](practice.md)

## 1. 区分四种不同证据

| 证据 | 可以说明什么 | 不能直接推出什么 |
| --- | --- | --- |
| 访谈中的具体经历 | 问题怎样发生、现有解决办法与成本 | 用户一定会采用尚未出现的产品 |
| 原型中完成任务 | 流程是否能理解，哪些地方卡住 | 实际系统可靠、用户会持续使用 |
| 真实使用与后续行为 | 在明确人群和窗口内的激活、返回、放弃原因 | 一定提高英语能力或愿意付费 |
| 学习表现与真实付款 | 特定任务上的变化、特定条件下的支付行为 | 对所有人有效或能长期盈利 |

不同假设需要不同证据。研究中出现相反结果时，优先修正问题定义、目标人群或范围，不先扩大功能。

## 2. 评审一个故意有问题的方案

假设方案：“所有想学英语的人都是用户；大家都觉得 AI 很好；先做背词、口语、社交、课程市场和 Android；免费不限量吸引人；看下载量和聊天时长；用户变多后再考虑内容、成本和学习效果。”

| 问题 | 对开发的影响 | 推荐的最小改法 |
| --- | --- | --- |
| 人群过宽，目标冲突 | 词库、任务、价格、交互无从取舍 | 按具体任务与可触达人群缩小首版 |
| 只有对 AI 的好感 | 可能没有需要解决的高频问题 | 看过去行为、替代方案与实际付出 |
| 首版包含多个独立业务 | 交付慢，无法知道什么带来价值 | 选择能验证关键假设的完整任务 |
| 免费不限量但每次有成本 | 使用增长可能放大亏损 | 估算免费与高频场景，验证合理边界 |
| 下载量 / 时长代替效果 | 奖励无效停留，无法证明学会 | 分开定义使用、学习和付费证据 |
| 内容与数据责任延后 | 已实现功能可能无法合法、可信地提供 | 开工前明确内容来源、数据范围与待核对事项 |
| 技术平台先行 | 分散精力而未验证新平台人群 | 根据用户需求与维护能力决定扩展 |

## 3. 产品决定怎样传给技术

| 产品规则 | 对后续设计的直接影响 |
| --- | --- |
| 同一次作答不能重复计分 | 请求标识、约束、事务与恢复路径 |
| 学习历史需要保留当时题面 | 内容版本、快照与删除规则 |
| 原型允许取消编辑 | SwiftUI 草稿与提交边界 |
| 免费额度需要控制服务成本 | 服务端额度、并发与失败重试预算 |
| 首版只面向一个地区和人群 | 内容、语言、渠道、设备与发布资料 |
| 需要判断是否真正学会 | 合理任务、评测口径与可追溯学习事件 |

这些是讨论入口，不要求第 9 项提前实现后续所有能力。只把已经确认的规则和关键未知交给开发；需要真实行为才能决定的部分留在验证计划中。

## 4. 足以开工，也允许推翻

P1～P3 的完成意味着“下一步做什么、为了验证什么、怎样判断结果”已经清楚，不意味着商业成功得到证明。若新证据改变核心任务，可以调整总路线中的默认功能顺序；保留 SwiftUI、Go、PostgreSQL 等已学能力，避免把学习顺序当作必须照搬的产品定义。
