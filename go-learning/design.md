# Go 设计补充：请求、数据库与失败边界

## 1. 先解释路径，再考虑分层

```text
HTTP Handler：方法 / 路径 / 大小 / JSON
→ 业务规则：规范化、字段校验、动作语义
→ 数据访问：参数化 SQL、Rows、事务与错误
→ 业务结果 → HTTP 状态与 JSON
```

配置、连接池和服务实例在启动时创建并注入需要的地方；不在每个请求里重建连接池。当前可以使用少量文件和具体类型，需要替代实现或明确测试边界时才抽 interface。

请求 context 传递到等待和 SQL；不要在中途用 Background 把取消链断开。后台任务需要独立生命周期时再显式设计。多个 Handler 本来就可能并发，共享 map、计数器或配置热更新必须有安全的访问方式。

## 2. 哪一层保证什么

| 规则 | 主要保证位置 | 必须验证的反例 |
| --- | --- | --- |
| term / level 输入合法 | API 规范化与校验，数据库守住声明的约束 | 空白、超长、未知等级、直接 SQL 非法写入 |
| 规范化后的 term 不重复 | 规范化后由数据库唯一约束裁决 | 并发相同输入，不能只靠先查后插 |
| 词条与备注一起保存 | 同一数据库事务 | 第二条写入失败，第一条不得残留 |
| 单个用户只能改自己的数据 | 未来认证身份与对象授权 | 当前教具没有用户模型，不能冒充验证了越权防护 |
| 连接能够回到池里 | 及时消费 / 关闭 Rows、结束事务、释放手动获取的连接 | 多次失败后池耗尽 |
| 写操作重复无额外业务效果 | 按动作设计的业务幂等协议 | 提交后断线重试，或同键不同载荷 |

当前词条唯一冲突会返回 409；这只防止同名词条重复，不等于“同一次请求重试返回原结果”的完整幂等实现。产品词条可能还涉及词性、语言与释义，同名唯一只是本轮练习假设。

## 3. 事务与错误处理

- Begin 成功后必须有 Commit 或 Rollback；pgxpool 的事务不能靠 context 取消自动当作已回滚。
- 事务里的所有语句都走同一个 Tx，不能中途用 Pool 执行希望参与事务的语句。
- 失败时回滚；原请求 context 已取消时，清理可使用独立且短超时的 context，不能无限等待。
- Query 多行结果要关闭 Rows、检查扫描错误与 Rows.Err；QueryRow 的错误通常在 Scan 时返回；Exec 要检查错误和 RowsAffected。
- 用错误类型或 SQLSTATE 做映射，唯一冲突、无记录、超时与未知内部错误不能一律返回 500 或 404。详细错误留在脱敏日志，外部返回稳定错误码。
- Commit 报错或响应丢失时可能需要核对结果；不要未经分析就重跑整个业务，更不能把慢 AI 调用放进持锁事务。

## 4. 评审练习与参考方向

| 有问题的实现 | 反例与改法 |
| --- | --- |
| 拼接 term 到 SQL 字符串 | 带引号输入改变语法或产生注入；值用参数，动态排序列用白名单 |
| SELECT 不存在后再 INSERT | 并发请求同时通过查询；依赖唯一约束并映射冲突 |
| 开事务、插词，再用 pool 插备注 | 第二条在另一连接，无法一起回滚；统一走 Tx |
| Query 后直接 return，不管 Rows | 高并发或错误路径耗尽资源；按使用方式消费 / 关闭并检查错误 |
| 每次请求启动 goroutine，但没人等它结束 | 请求结束后仍占资源；定义所有者、取消信号与完成信号 |
| 所有 panic 都恢复成 200 | 监控和客户端误认为成功；只在边界做适当恢复与错误响应，修根因 |
| 用 map 假数据库证明事务正确 | 没有验证真实数据库约束和连接行为；补 PostgreSQL 集成测试 |
| 日志输出完整请求和配置 | 可能包含凭据与用户内容；记录请求 ID、动作、状态、耗时等必要字段 |

评审时先说触发条件与影响，再给最小改法。不要仅用“上 ORM”“上框架”“上分布式锁”替代解释。
